## 2026-09-08｜M11 退款写操作与 Human-in-the-loop

### 目标与实现

- Refund Agent 新增 `request_refund` 写 Tool，仍只通过 `RefundService` 写 PostgreSQL。
- 确定性业务规则负责 ownership、支付状态、30 天期限、剩余可退金额、风险分流和幂等；LLM 只提取订单号、金额与原因。
- 金额不超过 100 元且近 30 天有效退款少于 2 次时自动完成，否则创建 `Refund + HumanReview` 并由 LangGraph `interrupt` 暂停。
- 管理员 Review API 使用 `Command(resume=...)` 恢复原 thread；approve 完成退款，reject 拒绝退款。
- `request_key = SHA-256(thread_id + order_id)` 配合数据库唯一约束，订单行锁串行化同订单写入，防止重复退款。
- Migration 新增 `refunds.request_key` 与 `human_reviews.thread_id`；Alembic 比较时忽略由官方 Checkpointer 管理的四张表。

### 验证证据

- Ruff format/lint：通过。
- `uv run pytest`：133 项通过。
- M11 定向测试：自动退款、人工分流、approve、reject、资格拒绝、ownership、超额与重复保护全部通过。
- 跨 HTTP 测试：customer 访问 Review API 返回 403；admin 查询 pending 并恢复 Graph 后，审核状态与退款状态持久化。
- 开发库升级至 `20260908_0002 (head)`；`alembic check` 无业务 Schema 漂移。
- 真实 `qwen3.8-27b` smoke：退款 Tool、PostgreSQL 写入、interrupt、approve、resume 全部通过。
- Docker 重建后 API、PostgreSQL、Redis、etcd、MinIO、Milvus 均 healthy。

### 遗留事项

- 风控仅为学习用固定阈值，没有 ML、多级审批、支付网关退款或资金对账。
- Review API 只有 pending 列表与单次 approve/reject，没有分页、审计查询和并发管理界面。

## 2026-09-08｜M10 Conversation Memory + LangGraph Persistence

### 目标

让 `/api/v1/chat` 的 `conversation_id` 对应持久化 LangGraph Thread，使同一 UUID 的多次请求恢复现有 Graph State，并保持不同 Conversation 隔离。

### 关键决策

- 直接使用官方 `AsyncPostgresSaver`，不创建 Memory Manager、Repository、Service 或 Strategy。
- `conversation_id` 的字符串形式直接作为 LangGraph `thread_id`；缺省 UUID 在 Graph 执行前由 ChatService 生成。
- `StateGraph.compile(checkpointer=...)` 启用持久化，FastAPI lifespan 管理 Saver 连接和 ChatService 生命周期。
- 应用启动时调用幂等 `checkpointer.setup()`，官方表不纳入业务 Alembic Migration。
- 每次请求只向 `messages` reducer 追加最新 user message，并重置单次执行字段 `tool_used=False`。
- ChatState 没有增加 memory、summary、profile 或 long-term memory 字段。
- Router 使用当前 Thread 的消息文本判断最新省略指代；Specialist 继续接收已有消息上下文。
- PostgreSQL 与业务数据共用实例，Redis 不参与 Conversation History。

### 实现范围

- 状态：已完成并通过 M10 验收。
- 新增 `langgraph-checkpoint-postgres`、Psycopg 3 binary，并使用异步 Saver。
- 官方 setup 创建 checkpoints、checkpoint_blobs、checkpoint_writes、checkpoint_migrations。
- 新增同会话订单追问、跨 Agent 退款追问、Conversation Isolation 和跨连接恢复测试。
- 新增显式真实多轮 smoke；未增加 Agent、Tool、业务能力或 RAG 技术。

### 验证证据

- M10 Checkpoint/Conversation 定向测试：通过。
- `uv run ruff format --check .` 与 `uv run ruff check .`：通过。
- `uv run pytest`：124 项通过。
- PostgreSQL 集成测试在关闭 Saver 连接后重新连接，相同 thread_id 恢复首次消息。
- 真实百炼多轮：第二轮“它现在是什么状态”恢复订单号并重新执行订单 Tool。
- 跨 Agent 多轮：“它有没有退款记录”从订单历史取得退款单号并执行 Refund Agent/Tool。
- Conversation Isolation：新 UUID 没有使用另一 Thread 的订单号或退款单号。
- Docker HTTP 使用同一 conversation_id 连续请求成功，对应 PostgreSQL 中生成 12 个 checkpoint。

### 问题与解决方案

- Psycopg 异步连接不支持 Windows 默认 ProactorEventLoop；integration 测试通过 pytest-asyncio 官方 loop factory hook 使用 SelectorEventLoop，Docker/Linux 路径不受影响。
- Order Agent 首次直接复用历史 Tool Result 回答“现在”状态；收紧既有 Prompt，要求新的当前状态查询必须刷新订单 Tool。
- 真实 Tool Arguments 的 JSON 空白不稳定；Smoke 改为解析 JSON 后比较语义字段，不比较原始字符串。

### 遗留事项

- 当前保存完整 State 和全部 checkpoint，没有摘要、Token Budget、消息裁剪或保留期限。
- 没有 Conversation 删除 API、用户级 Thread 列表或正式认证；UUID 仍不代表可信用户身份。
- Checkpoint 内容未实现应用级加密，适合当前本地学习环境。

## 2026-09-07｜M9 Hybrid Search + Reranker

### 目标

在不改变 Knowledge Agent 和业务能力的前提下，将 M8 Dense Retrieval 演进为 Milvus Dense+BM25+RRF，再通过百炼 Reranker 排序，并用小评估集比较三种方案。

### 关键决策

- 保留 `dense_search`，新增 `bm25_search`、`hybrid_search` 和 `rerank_candidates`，现有 `search` 成为 Hybrid+Reranker 最终入口。
- Collection 显式重建：content 使用中文 Analyzer，新增 `sparse_embedding`、BM25 Function 和 Sparse Inverted Index。
- Hybrid 使用两个 Milvus ANN Request，Dense 为 COSINE、Sparse 为 BM25，由原生 `RRFRanker(k=60)` 融合。
- Reranker 选择百炼 `qwen3-rerank`，位于 Hybrid 候选之后、Knowledge Agent Context 之前。
- 候选数为 10，最终 Top 3，Rerank 最低分 0.2。
- Markdown Loader 按 `##` 章节先切分，再应用 600/80 上限；8 个文档形成 24 个语义 Chunk。
- 使用 12 条 JSON 查询评估 Hit@1/Hit@3，不建立通用 Evaluation Framework。

### 实现范围

- 状态：已完成并通过 M9 验收。
- 新增发票、优惠券、会员、预售 4 份政策，知识库扩充为 8 文档。
- 新增 Milvus 原生 BM25、Hybrid+RRF 和百炼文本 Rerank。
- 新增 Retrieval Dataset、指标函数、评估脚本和真实结果报告。
- Knowledge Agent、Router、Supervisor 与公共 API 架构保持不变。
- 未实现 Query Rewrite、HyDE、Multi Query、Learned Sparse、Memory 或 Agent Evaluation。

### 真实评估结果

| Pipeline | Hit@1 | Hit@3 |
| --- | ---: | ---: |
| Dense Only | 1.00 | 1.00 |
| Dense + BM25 + RRF | 1.00 | 1.00 |
| Dense + BM25 + RRF + qwen3-rerank | 1.00 | 1.00 |

Dense 已在当前简单评估集上达到满分，因此 Hybrid 和 Reranker 没有改善 Hit 指标。Hybrid 对“预售商品 48 小时发货”等精确词查询提高了 Top-3 同主题集中度；Reranker 保持正确 Top 1，但在优惠券退款等查询中引入了较弱的后续候选。

### 验证证据

- M9 Retriever/Rerank/Evaluation 定向测试：12 项通过。
- `uv run ruff format --check .` 与 `uv run ruff check .`：通过。
- `uv run pytest`：119 项通过。
- 真实重建：8 文档、24 Chunk 成功写入 Dense+BM25 Collection。
- 真实 BM25 数字关键词、Hybrid+RRF、`qwen3-rerank` 与 Knowledge Agent smoke：通过。
- 12 条真实 Retrieval Evaluation 已输出并保存代表性排名变化。
- Docker API 重建后 Knowledge Chat 返回 HTTP 200，回答保留 source。

### 问题与解决方案

- `text-embedding-v4` 单批最多 10 条，24 Chunk 单次调用返回配置错误；在模型边界增加固定 10 条批处理，并通过 10+1 回归测试。
- 评估显示技术阶段增加不等于质量自动提升；保留真实满分指标和负向排名变化，没有通过修改标注或挑选样本制造提升。

### 遗留事项

- 12 条评估集仍过小且偏简单，无法证明 Hybrid/Reranker 的稳定收益。
- RRF k、候选数和 Rerank 阈值尚未通过更大评估集调优。
- 中文 Analyzer 和政策语料适合当前数据，不代表其他语言或真实企业知识库表现。

## 2026-09-07｜M7 Supervisor 与跨 Agent 协作

### 目标

不增加业务 Tool，让 complex 请求通过最小 Supervisor 顺序协调现有 Specialist，并汇总多个 Agent 的查询结果。

### 关键决策

- Router 在 M6 五条直接路径基础上增加 complex；简单请求继续绕过 Supervisor。
- Supervisor 复用 Structured Output 生成 2～3 步唯一顺序计划，步骤仅允许 order、refund、product。
- Supervisor 不接收 Tool Schema；业务数据仍只能由对应 Specialist 经 `BusinessTools` 和 M2 Service 查询。
- State 只增加 `plan`、`current_step`、`agent_results` 和 `tool_used`，分别支持顺序推进、结果汇总与单步 Tool 上限。
- 三个 Specialist、Prompt 和 Tool Isolation 原样复用；Tool 节点根据当前计划步骤决定允许调用的 Tool。
- 前序 Agent 的结果保留在消息和 `agent_results` 中，使后续 Agent 可以使用已发现的退款单号或 SKU。
- 不实现并行、Replanning、DAG、Subgraph、Memory 或失败恢复框架。

### 实现范围

- 状态：已完成并通过 M7 验收。
- 新增 `complex` Route 和 `SupervisorPlan` typed schema。
- Graph 新增 supervisor、supervisor_step、supervisor_final 三个职责明确的节点。
- 支持 order→refund 与 order→product 顺序协作，并在最后生成自然语言汇总。
- 真实 smoke 缩减为一个简单订单请求和一个复杂订单+退款请求，避免重复历史真实模型验收。
- 未增加业务 Tool、Agent 类型、公共 API 或基础设施。

### 验证证据

- M7 Schema/Workflow 定向测试：12 项通过。

- 简单 order/refund/general 路径继续绕过 Supervisor。
- complex order→refund 与 order→product 路径按计划顺序执行、收集结果并进入 supervisor_final。

### 问题与解决方案

- 真实模型有一次进入 Refund Agent 后直接复用 Order Tool 的退款摘要，跳过 Refund Tool；安全诊断确认路径后，收紧 Refund Prompt，要求发现退款单号时必须用自己的隔离 Tool 确认最新状态。没有增加自动重试掩盖问题。

### 遗留事项

- Supervisor 只执行一次静态顺序计划，不会 Replan、并行或处理部分步骤失败。
- 复杂请求必须能由现有三个只读 Specialist 完成，仍不能创建退款或执行其他写操作。
- State 不持久化，身份仍使用 `DEVELOPMENT_USER_EMAIL`。

## 2026-09-07｜M5 LangGraph 基础工作流

### 目标

不增加业务能力，只将 M4 已跑通的模型与 Tool Calling 手写循环迁移到最小 LangGraph Workflow，学习 State、Node、Edge 和 Conditional Edge。

### 关键决策

- 使用 LangGraph `StateGraph`，不使用预构建 Agent、`ToolNode`、LangChain 消息封装或自定义 Graph Framework。
- State 只有追加式 `messages`，直接承载现有 OpenAI-compatible 消息字典。
- 只有 `model` 与 `tools` 两个节点；条件边根据最后一条模型消息是否带 `tool_calls` 决定进入 Tool 或结束。
- Tool 节点继续调用 `BusinessTools.run`，M4 的 Tool Schema、M2 Service 和 `DEVELOPMENT_USER_EMAIL` ownership 规则均保持不变。
- 第二次模型调用仍请求 Tool 时终止为 Provider Error，保持当前单轮 Tool Calling 边界。
- Graph 不配置 Checkpointer；`conversation_id` 仍只是 HTTP 关联标识。
- `/api/v1/chat` 的 Request、Response 和 Error Contract 不变。

### 实现范围

- 状态：已完成并通过 M5 验收。
- 新增一个 Workflow 模块，在应用启动时编译 Graph。
