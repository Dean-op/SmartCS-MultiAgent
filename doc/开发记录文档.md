## 2026-09-07｜M3 LLM 接入与结构化输出

### 目标

通过阿里云百炼 OpenAI-compatible API 接入 `qwen3.8-27b`，将 M1 Mock Chat 替换为真实模型边界，并验证 JSON Object 到 Pydantic typed result。

### 关键决策

- 使用 OpenAI Python SDK 3.x `AsyncOpenAI`，不提前引入 LangChain。
- 只实现一个具体 `BailianModel`，不创建 Provider Interface、Factory、Registry 或 Prompt 管理框架。
- 普通生成和 Structured Output 共用模型配置、SDK 客户端、错误映射和日志。
- Structured Output 使用 `response_format=json_object`，Prompt 提供 JSON Schema，再经 Pydantic 校验。
- Chat 请求字段保持不变，响应 `mode` 从 `mock` 更新为 `llm`。
- 应用缺少模型配置时仍可启动，Chat 返回统一 `model_not_configured`。
- timeout 和重试使用 SDK 内置能力，不维护自定义退避循环。
- 默认 pytest 和基础 smoke 不发起真实模型调用；真实调用只由显式 LLM smoke 执行。

### 实现范围

- 状态：已完成并通过 M3 验收。
- 新增百炼配置、`BailianModel`、模型异常和 `MessageAssessment`。
- ChatService 使用真实模型内容，并包含不伪造订单查询、数据库修改和退款执行的客服约束。
- 新增 Provider 错误到 M1 Error Contract 的映射及 OpenAPI 502/503/504 文档。
- 新增 provider/model/operation/latency/outcome 安全日志字段。
- 新增显式 `scripts/llm_smoke_test.py`，验证普通生成和 Structured Output。
- 未实现 Tool Calling、Agent、LangGraph、正式 Router、Memory、Embedding 或 RAG。

### 验证证据

- OpenAI SDK：uv 锁定 `3.8.0`。
- `uv run ruff format --check .`：72 个 Python 文件格式正确。
- `uv run ruff check .`：通过。
- 显式清空子进程 API Key 后运行 `uv run pytest`：79 项离线测试通过，包含 M0/M1/M2 全部回归且未访问百炼。
- Docker Compose：API、PostgreSQL、Redis、etcd、MinIO、Milvus 六服务 healthy。
- 基础 smoke：通过，验证 readiness、Swagger 和 Chat validation，不访问模型。
- 真实 LLM smoke：`qwen3.8-27b` 普通文本生成成功，返回 58 个字符。
- 真实 Structured Output：JSON Object 经 Pydantic 转为 `MessageAssessment`，总 smoke 耗时约 3.76 秒。
- Docker Chat：返回 HTTP 200、`mode=llm`，模型日志记录 success 和 latency。
- 日志 Secret 扫描：Key 与专属 Host 均无命中；日志仅含允许字段。

### 问题与解决方案

- OpenAI SDK 3.x 使用 `httpx2` logger，最初在 INFO 日志中记录专属请求 URL；增加回归测试并将 `httpx2` 与 `httpx` 同时设为 WARNING，复验日志无专属 Host 和 Key。
- Alembic `fileConfig` 默认禁用未列出的应用 logger，导致组合测试无法捕获模型日志；改为 `disable_existing_loggers=False` 并增加迁移回归测试。
- Provider 的 403 `insufficient_quota` 最初被归类为鉴权失败；新增真实错误对应测试，改为 `provider_rate_limited`。
- 初始 `qwen3.7-plus` 测试 Key 没有可用额度，切换到有免费额度的 `qwen3.8-27b` 后普通文本成功。
- `qwen3.8-27b` 对 strict JSON Schema 把单个对象包成数组；回到 Structured Output 的学习目标，采用官方支持的 JSON Object 模式，并由 Pydantic 完成 Schema 校验和 typed 转换，不增加供应商补丁。

### 提交

- 设计规格：`docs(m3): 添加 LLM 接入与结构化输出设计`
- M3 实现：`feat(llm): 接入 M3 百炼模型与结构化输出`
- 实现提交包含中文 Description，说明模型边界、错误映射、测试与真实 Smoke 结果。

### 遗留事项

- 当前没有 Tool、业务操作、Memory 或多轮上下文；每个 Chat 请求仍是独立调用。
- 没有 Token/Cost 指标或 OpenTelemetry，这些属于后续可观测性里程碑。

## 2026-09-06｜M2 PostgreSQL 业务数据层

### 目标

建立后续 Tool 和 Agent 可通过 Service 安全查询的真实电商数据基础，完成 PostgreSQL 业务建模、SQLAlchemy 异步访问、Alembic Migration、幂等 Seed 及 Repository/Service 边界。

### 关键决策

- 使用 UUID 主键；开发 Seed 使用 UUID v5 保持重复运行结果稳定。
- 金额使用 PostgreSQL `NUMERIC(12,2)` 和 Python `Decimal`，不使用 float。
- 订单、支付、物流、退款、审核与角色使用 PostgreSQL Named Enum。
- 每个异步任务独立使用 `AsyncSession`；Repository 不 commit，事务由调用方管理。
- 使用具体 Repository 与 Service，不引入通用 BaseRepository、GenericService 或 Unit of Work 框架。
- Repository 返回 ORM aggregate，Service 在 Session 内映射为 frozen DTO；嵌套集合使用 tuple。
- ownership 查询在 SQL 中同时约束 `user_id` 与 `order_number`，不在内存中事后判断。
- Alembic 是唯一正式 Schema 管理入口；API 启动不调用 `create_all`，Seed 也不自动运行。
- M2 不新增公共 CRUD API，避免提前引入认证和授权语义。

### 实现范围

- 状态：已完成并通过 M2 验收。
- 新增 User、Product、Order、OrderItem、Shipment、Refund、HumanReview 七个实体。
- 新增 7 组 Named Enum、必要的 PK/FK/Unique/Check/Index 和 UTC 时区列。
- 新增 AsyncEngine、Session Factory、4 个具体 Repository、4 个 Service 和 Service DTO。
- 新增 Alembic async 环境及初始业务 Schema revision。
- 新增 6 用户、12 商品、24 订单、12 物流、5 退款、3 审核的幂等 Seed。
- 新增独立 PostgreSQL 测试库和 Migration/Seed/Service 集成测试。
- 未实现认证、JWT、业务写 API、退款风控、Agent、LLM、LangGraph、Redis Session 或 RAG。

### 验证证据

- `uv lock --check` 与 `uv sync --frozen --all-groups`：通过，共解析 39 个包。
- `uv run ruff format --check .`：64 个 Python 文件格式正确。
- `uv run ruff check .`：通过。
- `uv run pytest`：50 项测试通过，包含 Migration、Seed、测试库安全、Service 和全部 M0/M1 回归。
- 独立 `ecommerce_agent_test`：成功执行 `upgrade head → downgrade base → upgrade head`，测试后自动删除。
- 开发库：`20260906_0001 (head)`。
- `uv run alembic check`：`No new upgrade operations detected`，ORM 与 Migration 无 drift。
- Seed 连续执行数量均为 users=6、products=12、orders=24、shipments=12、refunds=5、reviews=3。
- Service 查询：ownership、Items→Product、Shipment、Refund→HumanReview 均通过，跨用户订单查询返回 `None`。
- Docker Compose：API、PostgreSQL、Redis、etcd、MinIO、Milvus 六服务 healthy。
- M0 readiness 与 M1 Chat/Swagger smoke：通过。

### 问题与解决方案

- session-scope 测试 Engine 最初跨 pytest event loop 保留连接；集成测试改用 `NullPool`，每次操作在所属 loop 内建立和关闭连接。
- Seed 中一条 ¥200 退款超过所属订单 ¥189；测试发现后修正为 ¥150，并保留“退款金额不超过订单金额”断言。
- PostgreSQL Enum 在 downgrade 时不会仅靠删表可靠清理；Migration 显式按反向顺序 drop 7 个 Enum type。
- frozen DTO 的嵌套 list 仍可变；改为 tuple 并增加回归测试，避免未来 Tool 修改查询结果集合。

### 提交

- 设计规格：`docs(m2): 添加 PostgreSQL 业务数据层设计`
- M2 实现：`feat(data): 建设 M2 PostgreSQL 业务数据层`
- 提交描述记录数据模型、Migration、Seed、查询边界和验收结果。

### 遗留事项

- 当前 Service 只提供读取能力，退款创建与状态变更事务属于后续业务里程碑。
- User 仅预留 `password_hash`，没有注册、登录、密码验证、JWT 或 Authorization。
- HumanReview 仅有数据结构，没有审批 API、风控、LangGraph interrupt/resume。
- `updated_at` 依赖 ORM 写路径更新；若未来允许外部 SQL 写入，再评估数据库触发器。

## 2026-09-06｜M1 FastAPI API 层建设

### 目标

建立版本化、可验证且与未来 LangGraph Workflow 解耦的 HTTP API 基础，新增不调用模型的 Mock Chat API，并统一请求校验与错误响应。

### 关键决策

- 业务 API 使用 `/api/v1` 前缀；M0 的 `/health/live` 与 `/health/ready` 保持不变。
- Chat 请求只接受 `message` 和可选 `conversation_id`，明确拒绝客户端提交的 `user_id` 等额外字段。
- `message` 去除首尾空白后长度限制为 1～4000，使用严格字符串校验。
- `conversation_id` 只作为关联标识，不代表可信身份；缺省时由服务端生成，但 M1 不持久化会话。
- Mock 行为放在具体 `ChatService` 中，通过 FastAPI dependency 注入，不创建抽象基类。
- API 错误统一为 `error.code/message/details`，不回显请求正文、原始异常或 traceback。
- 保留 FastAPI 默认 `/docs` 与 `/openapi.json`，为 Chat 显式声明 200/400/422/500 Schema。
- 当前没有跨域前端、认证上下文或请求链路需求，因此不增加 CORS 和 Middleware。

### 实现范围

- 状态：已完成并通过 M1 验收。
- 新增 Chat Request/Response Schema、Mock Chat Service、v1 Router。
- 新增 validation、application、HTTP 和 unexpected exception handlers。
- 补充 OpenAPI 元数据、Chat ErrorResponse 文档和 Swagger 验证。
- 扩展 smoke test 与 README；未新增第三方依赖。
- 未实现 LLM、LangGraph、Agent、JWT、Redis Session、SSE 或其他 M2+ 能力。

### 验证证据

- `uv run ruff check .`：通过。
- `uv run pytest`：29 项测试通过，包含 Chat、非法输入、错误处理、OpenAPI、Swagger 和全部 M0 测试。
- `docker compose up -d --build --wait`：构建成功，六个服务均 healthy。
- M1 smoke test：通过，验证 M0 dependencies、Swagger、Chat 和 validation。
- 真实 HTTP Contract：13/13 检查通过，包括正常请求、7 类非法输入、404 与 405。
- `/openapi.json`：包含 `/api/v1/chat` 及 200/400/422/500 响应 Schema。
- `/docs`：返回 200，Swagger UI 可用。
- `/health/ready`：返回 200，PostgreSQL、Redis、Milvus 均为 `ok`。

### 问题与解决方案

- FastAPI 默认 validation、404、405 与 500 响应格式不统一；通过一组轻量 exception handlers 映射到稳定 ErrorResponse，同时保留正确 HTTP 状态码。
- 为避免未来接入 LangGraph 时修改 HTTP Contract，将 Mock 执行逻辑隔离到 Chat Service，Router 只负责协议转换和依赖调用。

### 提交

- M1 实现：`feat(api): 建设 M1 FastAPI API 层`

### 遗留事项

- 当前没有身份认证，`conversation_id` 不能用于授权或证明用户身份。
- Chat 只返回无状态 Mock 响应；LangGraph、Redis Session 与流式输出属于后续里程碑。
- CORS、请求 ID 与访问控制在出现真实调用方和安全需求后再设计。

## 2026-09-06｜M0 工程骨架与本地基础设施初始化

### 目标

从零建立 `ecommerce-ai-agent` 的 Python 工程基础和本地 Docker Compose 环境，为后续 FastAPI、LangGraph、Agent、Tool、RAG 与 Evaluation 模块提供稳定扩展点。

### 关键决策

- 在当前 Git 仓库根目录初始化，不增加同名嵌套目录。
- 使用 `src/ecommerce_ai_agent` 布局和 `uv.lock`。
- M0 只保留实际使用的应用依赖，不提前安装 AI 与业务依赖。
- Compose 编排 API、PostgreSQL、Redis、etcd、MinIO、Milvus 六个服务。
- readiness 实际探测 PostgreSQL、Redis 和 Milvus；liveness 不依赖外部服务。
- 使用命名卷持久化五个有状态服务，Redis 开启 AOF。
- 不增加 Makefile，使用标准命令和跨平台 Python smoke test。

### 实现范围

- 状态：已完成并通过 M0 验收。
- 初始化 `pyproject.toml`、`uv.lock`、Python 版本约束和开发工具配置。
- 创建最小 FastAPI 应用、环境配置、JSON 日志、liveness 与 readiness。
- 创建非 root API 镜像以及六服务 `compose.yaml`。
- 配置 PostgreSQL、Redis、etcd、MinIO、Milvus 五个命名卷，Redis 启用 AOF。
- 创建 `.env.example`、`.gitignore`、`.dockerignore`、README 和 smoke test。
- 未创建 Agent、LLM、RAG、业务模型、Migration、Milvus Collection 或其他后续模块。

### 验证证据

- `uv lock --check`：通过。
- `uv sync --frozen --all-groups`：通过，项目可安装。
- `uv run ruff check .`：通过。
- `uv run pytest`：14 项测试通过。
- `docker compose config --quiet`：通过。
- `docker compose build api`：通过，容器内从锁文件安装项目成功。
- `docker compose ps`：API、PostgreSQL、Redis、etcd、MinIO、Milvus 六个服务均为 healthy。
- Service Name DNS：API 容器成功解析 `postgres`、`redis`、`milvus`、`etcd`、`minio`。
- `scripts/smoke_test.py`：通过，readiness 返回 PostgreSQL、Redis、Milvus 均为 `ok`。
- 持久化验证：五个命名卷的测试标记在全容器强制重建后均保留，验证后已全部清理。

### 问题与解决方案

- MinIO 社区仓库已经归档，但 Milvus 2.6.22 官方 Standalone Compose 仍依赖固定的历史兼容镜像。M0 保持既定架构并锁定镜像版本，将生产化替换评估列为后续风险。
- 新版 Starlette 的同步 `TestClient` 产生弃用警告；测试改用 `httpx.AsyncClient` 与 ASGI transport，最终测试输出无警告。
- API healthcheck 周期性触发 `httpx` INFO 请求日志；将第三方 HTTP 客户端日志级别调整为 WARNING，保留应用日志并减少噪声。
- PostgreSQL 数据库注释属于共享对象，持久化验证应使用 `shobj_description`，不能使用普通对象的 `obj_description`。
- `docker compose wait` 等待的是容器停止，不适合等待长期服务健康；验收改用有截止时间的 health 状态轮询。

### 遗留事项

- MinIO 历史社区镜像的维护与安全风险需在生产化前重新评估。
- 当前健康检查只验证基础连接，不验证业务表、LangGraph Checkpoint 或 Milvus Collection；这些属于后续里程碑。
- 当前是本地开发配置，没有 TLS、Secret Manager、网络隔离等生产安全加固。
