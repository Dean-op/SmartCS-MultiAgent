# M0 工程骨架与本地开发基础设施设计

## 1. 文档状态

- 项目名称：`ecommerce-ai-agent`
- 里程碑：M0——工程骨架与本地开发基础设施初始化
- 状态：已确认，待实施
- 日期：2026-09-06

## 2. 目标

在当前 Git 仓库根目录建立可长期演进的 Python 工程基础，并提供可重复启动和验证的本地 Docker Compose 环境。M0 只负责应用外壳、配置、健康检查、基础日志、依赖管理和基础设施，不实现任何 Agent 或电商业务能力。

完成后，新开发者应能从 `.env.example` 建立本地配置，通过 `uv` 安装开发环境，通过 Docker Compose 启动完整 M0 服务，并使用自动化测试和 smoke test 判断环境是否可用。

## 3. 范围边界

### 3.1 本次实现

- `uv` 管理的 Python 3.12+ 项目与锁文件
- `src` 布局的可安装 Python 包
- 最小 FastAPI 应用
- 环境变量配置和安全的示例配置
- 最小结构化日志配置
- API liveness 与 readiness 健康检查
- API、PostgreSQL、Redis、etcd、MinIO、Milvus Standalone 的 Docker Compose 编排
- 有状态服务的命名卷持久化
- pytest 自动化测试和运行态 smoke test
- 本地开发 README
- 可持续追加的开发记录文档

### 3.2 明确不实现

M0 不引入或实现 LLM、百炼 API、Embedding、LangChain、LangGraph、Checkpoint、Agent、Tool Calling、JWT、业务模型、Alembic 业务迁移、Milvus Collection、RAG、Celery Worker、OpenTelemetry、Streamlit 或 Evaluation。

## 5. Python 工程设计

### 5.1 运行时

- 项目声明：Python `>=3.12,<3.14`
- 容器运行时：`python:3.12.14-slim-bookworm`
- 包名：`ecommerce_ai_agent`
- 分发名：`ecommerce-ai-agent`

允许本机已安装的 Python 3.12 或 3.13 运行开发环境，同时使用 Python 3.12 作为容器基线，降低未来 AI 生态依赖兼容风险。

### 5.2 依赖

只加入 M0 实际使用的运行时依赖：

- `fastapi`
- `uvicorn[standard]`
- `pydantic-settings`
- `asyncpg`
- `redis`
- `httpx`

开发依赖：

- `pytest`
- `pytest-asyncio`
- `ruff`

不提前安装 LangChain、LangGraph、Celery、SQLAlchemy、Alembic、Milvus Python SDK 或 OpenTelemetry。Milvus readiness 使用管理 HTTP 端点完成，不需要为一次健康探测引入 SDK。

### 5.3 配置

`config.py` 使用 `pydantic-settings`，配置来源为环境变量；本机直接运行时可读取未提交的 `.env`。配置至少包含：

- 应用环境、日志级别和 API 监听地址
- PostgreSQL host、port、database、user、password
- Redis host、port
- Milvus host、gRPC port、management port
- 健康检查超时

`.env.example` 使用可读的开发占位值，不包含真实 Secret。`.env`、`.env.*` 默认忽略，但 `.env.example` 明确允许提交。Compose 在容器环境中显式把依赖 host 覆盖为 `postgres`、`redis`、`milvus`，保证服务间通信不依赖 `localhost`；本机直接运行 API 时则可使用 `localhost`。

## 6. API 与健康检查

FastAPI 只提供两个 M0 端点：

- `GET /health/live`：只证明 API 进程正在响应，返回 HTTP 200。
- `GET /health/ready`：并发检查 PostgreSQL、Redis 和 Milvus；全部可用时返回 HTTP 200，否则返回 HTTP 503，并以不含凭据的结构返回各依赖状态。

探测方式：

- PostgreSQL：建立短连接并执行 `SELECT 1`
- Redis：建立连接并执行 `PING`
- Milvus：访问 `http://milvus:9091/healthz`

每个探测设置短超时。readiness 失败写入警告日志，但不输出密码、连接串或异常中的敏感数据。应用启动日志只记录应用名、环境和日志级别。

## 7. Docker 设计

### 7.1 镜像策略

M0 锁定明确镜像标签，不使用 `latest`：

| 服务 | 镜像基线 |
| --- | --- |
| API 构建 | `python:3.12.14-slim-bookworm` + `ghcr.io/astral-sh/uv:0.12.10` |
| PostgreSQL | `postgres:16.15-bookworm` |
| Redis | `redis:7.4.11-bookworm` |
| etcd | `quay.io/coreos/etcd:v3.5.25` |
| MinIO | `minio/minio:RELEASE.2024-05-28T17-19-04Z` |
| Milvus | `milvusdb/milvus:v2.6.22` |

实施时先验证全部标签可以拉取。etcd 和 MinIO 版本遵循 Milvus 2.6.22 官方 Standalone Compose 的兼容组合；Milvus 服务本身使用当前确定的 2.6.22 版本。

### 7.2 API 镜像

Dockerfile 使用分层构建缓存：先复制 `pyproject.toml` 和 `uv.lock` 安装锁定依赖，再复制源码安装项目。最终容器以非 root 用户运行，执行锁文件对应环境中的 Uvicorn。`.venv`、`.git`、`.env`、测试缓存和本地数据不进入构建上下文。

### 7.3 Compose 服务关系

```text
etcd ───┐
        ├──> milvus ──┐
minio ──┘             │
                      ├──> api
postgres ─────────────┤
redis ────────────────┘
```

- 六个服务使用显式网络 `ecommerce-agent-network`。
- Milvus 通过 `etcd:2379` 和 `minio:9000` 访问依赖。
- API 通过 `postgres:5432`、`redis:6379` 和 `milvus:9091` 访问依赖。
- `depends_on` 的健康条件只用于改善启动顺序，API 自身 readiness 仍是运行时事实来源。
- 开发环境暴露 API、PostgreSQL、Redis、Milvus gRPC/management、MinIO API/console 端口，便于本机诊断。

### 7.4 数据持久化

使用 Compose 命名卷：

- `postgres_data`
- `redis_data`
- `etcd_data`
- `minio_data`
- `milvus_data`

Redis 启用 AOF。`docker compose down` 保留数据；只有显式执行 `docker compose down -v` 才删除数据。持久化验收会在卷内写入不属于业务模型或 Collection 的测试标记，强制重建容器后验证标记仍存在，再清理测试标记。

## 8. 测试和验收设计

### 8.1 本地静态与单元验证

- `uv lock --check`：锁文件与项目声明一致
- `uv sync --frozen --all-groups`：依赖可解析并安装
- `uv run ruff check .`：代码质量检查
- `uv run pytest`：配置、liveness、readiness 成功/失败分支测试
- `docker compose config --quiet`：Compose 结构与变量插值有效

### 8.2 容器与集成验证

- 构建 API 镜像
- 启动全部六个服务并等待健康
- 确认所有容器状态和 health 状态
- 调用 `/health/live` 和 `/health/ready`
- 检查 readiness 返回 PostgreSQL、Redis、Milvus 均可用
- 从 API 容器内解析并访问各 Compose Service Name
- 执行跨平台 `scripts/smoke_test.py`
- 写入持久化标记，执行容器强制重建，验证五个命名卷的数据保留，再清理标记

若完整 Compose 因机器资源不足无法稳定运行，应保留失败证据并明确报告，不能把仅通过配置解析视作 M0 完成。

## 9. README 设计

README 面向首次接触项目的开发者，包含：

- M0 的范围和非目标
- 环境要求
- 复制 `.env.example` 为 `.env`
- `uv` 本地安装与测试
- Compose 构建、启动、停止、查看状态和日志
- liveness、readiness 与 smoke test 命令
- 普通停止与删除数据卷的区别
- 常见问题：端口占用、Docker 内存、健康检查失败、首次拉取较慢
- 后续里程碑边界

不增加 Makefile。当前主要开发环境是 Windows，README 和跨平台 Python 脚本已经覆盖必要命令，引入 Makefile 只会增加额外工具依赖。

## 10. 开发记录

创建 `doc/开发记录文档.md`。文档顶部说明维护规则，正文按日期倒序记录：目标、关键决策、实现范围、验证证据、问题与解决方案、提交和遗留事项。每次功能变更完成验证后，与对应代码一起更新并提交。

## 11. 错误处理与安全

- 应用配置缺失或非法时快速失败，并给出字段级错误，不输出 Secret 值。
- 健康接口不返回连接串、密码或原始异常堆栈。
- `.env`、私钥、日志、缓存、虚拟环境和本地持久化数据全部忽略。
- Compose 示例凭据仅用于本地开发，并在 README 与 `.env.example` 中明确提示不得用于共享或生产环境。
- API 容器使用非 root 用户；本地服务不宣称具备生产安全加固。

## 12. 已知风险与处理

### 12.1 MinIO 社区镜像维护状态

截至 2026-09，MinIO 社区仓库已归档，历史预构建镜像不再维护。由于项目既定方案明确要求 Milvus Standalone + MinIO，且 Milvus 2.6.22 官方 Standalone Compose 仍使用 `RELEASE.2024-05-28T17-19-04Z`，M0 采用该兼容版本完成本地开发环境，但将其记录为后续生产化前必须重新评估的供应链和安全风险。

### 12.2 资源占用

Milvus、etcd 和 MinIO 比普通 API 开发环境更耗资源。README 会提示 Docker Desktop 资源要求；验收以当前机器的真实运行结果为准。

### 12.3 健康检查边界

M0 readiness 只验证连接和基本响应，不验证业务表、LangGraph Checkpoint 或 Milvus Collection，因为这些明确属于后续里程碑。

## 13. M0 完成判定

只有以下条件全部满足才判定 M0 完成：

1. `uv` 锁定、安装、lint 和 pytest 通过。
2. Compose 配置解析和 API 镜像构建通过。
3. 六个服务均成功运行，PostgreSQL、Redis、etcd、MinIO、Milvus 和 API 健康检查通过。
4. API readiness 实际确认 PostgreSQL、Redis 和 Milvus 可达。
5. Compose Service Name 通信验证通过。
6. 命名卷在容器重建后保留测试数据。
7. Secret 与本地数据未进入 Git。
8. README、`.env.example`、smoke test 和开发记录可供后续开发使用。
9. 未实现任何 M0 明确禁止的后续能力。
