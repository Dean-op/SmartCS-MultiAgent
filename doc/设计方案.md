## 1. 项目定位

**项目名称：E-commerce AI Agent**

定位为一个面向电商售前/售后的 **Multi-Agent 智能客服与业务执行系统**。

系统不仅回答问题，还能根据用户意图调用真实业务能力：

```text
用户自然语言
    ↓
识别意图
    ↓
选择 Agent
    ↓
调用业务 Tool / 检索知识库
    ↓
执行订单、物流、退款等业务
    ↓
高风险操作进入人工审核
    ↓
生成最终回答
```

项目目标不是模拟“大型互联网公司全部基础设施”，而是实现一个：

**业务闭环完整 + Agent 架构清晰 + 可评估 + 可观测 + 能讲透的简历项目。**

---

## 2. 核心设计原则

### 2.1 模块化单体，而不是微服务

第一版采用：

```text
一个 FastAPI 服务
+
PostgreSQL
+
Redis
+
Milvus
+
Celery Worker
```

不拆微服务。

原因是本项目真正需要展示的是：

```text
Agent Engineering
RAG
Workflow
Tool Calling
Memory
Evaluation
```

而不是服务治理。

因此采用：

> **Modular Monolith（模块化单体）**

各业务模块逻辑隔离，但运行在一个 Python 服务中。

---

### 2.2 Agent 不直接操作数据库

整个系统必须严格保持：

```text
Agent
↓
Tool
↓
Service
↓
Repository
↓
Database
```

例如退款：

```text
Refund Agent
    ↓
create_refund Tool
    ↓
RefundService
    ↓
RefundRepository
    ↓
PostgreSQL
```

职责分别是：

| 层          | 负责什么              |
| ---------- | ----------------- |
| Agent      | 理解、推理、决策          |
| Tool       | 将 Agent 能力连接到业务系统 |
| Service    | 实现业务规则            |
| Repository | 数据访问              |
| Database   | 保存事实数据            |

这样可以避免 LLM 和业务逻辑耦合。

## 4. Agent 架构

我们最终只保留 **3 个业务 Agent + 1 个 Supervisor**。

### Order Agent

负责：

```text
订单查询
订单状态
物流状态
预计送达时间
商品信息
```

主要 Tools：

```text
get_order
get_logistics
get_product
```

---

### Refund Agent

负责：

```text
退款资格判断
退款金额计算
退款申请
退款状态查询
```

Tools：

```text
check_refund_eligibility
calculate_refund
create_refund
get_refund_status
```

高风险退款：

```text
Refund Agent
      ↓
Risk Check
      ↓
超过阈值
      ↓
Human Review
      ↓
Approve / Reject
```

---

### Knowledge Agent

负责企业知识问答：

```text
退款政策
物流政策
售后政策
商品说明
服务规则
```

工作方式：

```text

 ↓
RAG
 ↓
Retrieve Documents
 ↓
Rerank
 ↓
Grounded Answer
```

---

### Supervisor

Supervisor 不负责具体业务。

负责：

```text

执行顺序

```

例如：

```text

                ↓

         ↓             ↓

         │             │
    查询物流       查询退款规则
         └──────┬──────┘
                ↓
          Refund Agent
                ↓
          判断退款资格
```

## 5. Router 设计

不是所有请求都进入 Supervisor。

设计：

```text
用户请求
   ↓
Router
   │
   ├── order
   ├── refund
   ├── knowledge
   └── complex
```

简单请求直接进入 Agent：

```text
“订单 A1001 到哪了？”

→ Order Agent
```

复杂请求：

```text
“订单还没到，如果不能按时到就退款。”

→ Supervisor
```

这样做有两个收益：

```text
降低 Token 消耗
降低响应延迟
```

这是以后一个很好的简历优化点。

## 6. LangGraph 设计

LangGraph 作为系统的**工作流编排核心**。

官方将 LangGraph 定位为面向长运行、有状态 Agent 的低层 orchestration runtime，核心能力包括 durable execution、streaming、human-in-the-loop 和 persistence。

其核心概念非常简单：

```text
State
Node
Edge
```

官方 Graph API 也是以这三个概念描述工作流。

我们的 Graph：

```text
START
  ↓
Safety
  ↓
Router
  ↓
┌───────────────┬─────────────────┐
│               │                 │
Order         Refund          Knowledge
│               │                 │
└───────────────┴────────┬────────┘
                         │
                     Supervisor
                         │
                         ↓
                 Human Review?
                    │       │
                   No      Yes
                    │       │
                    │    interrupt
                    │       │
                    │    resume
                    └───┬───┘
                        ↓
                 Response Builder
                        ↓
                       END
```

LangGraph v1 的核心 Graph API 已稳定，State、Node、Edge 等执行模型继续保持兼容，因此项目直接以 **LangGraph 1.x** 为基线。

## 7. Agent 实现策略

这里不全部手写 Agent Loop。

采用：

```text
LangGraph
      ↓
负责系统级 Workflow

LangChain create_agent
      ↓
负责单个 Specialist Agent
```

也就是：

```text
              LangGraph
                 │
         Router / Supervisor
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
   create_agent create_agent create_agent
     Order      Refund     Knowledge
```

原因：

LangChain v1 已将 `create_agent` 作为标准 Agent API，而且其底层就是 LangGraph；LangGraph 自身旧的 `create_react_agent` 已被弃用。

这样既能：

* 学 LangGraph 编排；
* 学 Tool Calling；
* 又不会把大量时间浪费在重复实现 Agent Loop。

## 9. Memory 设计

不设计过度复杂的“永久 AI 记忆”。

采用两层即可。

### Short-term Memory

Redis：

```text
session_id
conversation history
current order context
current task
```

例如：

```text
用户：
查一下 A1001。

Agent：
正在运输。

用户：
它什么时候能到？
```

Redis 保存：

```text
current_order_id = A1001
```

Agent 就能知道“它”指什么。

---

### Long-term Business State

PostgreSQL：

```text
User
Order
Refund
Product
HumanReview
```

特别注意：

> 用户订单属于业务事实，不属于 Agent Memory。

## 11. Human-in-the-loop

核心场景：

```text
低风险操作
↓
自动执行
```

例如：

```text
查询订单
查询政策
查询退款状态
```

高风险操作：

```text
高金额退款
异常退款
风险用户
```

流程：

```text
Refund Agent
      ↓
risk_score
      ↓
High Risk
      ↓
LangGraph interrupt
      ↓
HumanReview
      ↓
Approve / Reject
      ↓
Graph Resume
```

Human-in-the-loop 本身就是 LangGraph 的一等能力，因此不用自己设计复杂的暂停恢复系统。

## 17. Python 技术栈

### 核心技术栈

| 层               | 技术                    | 用途                   |
| --------------- | --------------------- | -------------------- |
| Language        | **Python 3.12+**      | 主语言                  |
| Package Manager | **uv**                | 依赖和虚拟环境              |
| API             | **FastAPI**           | HTTP / SSE           |
| Validation      | **Pydantic 2**        | Schema / Config      |
| Agent           | **LangChain 1.x**     | Model / Tool / Agent |
| Workflow        | **LangGraph 1.x**     | Multi-Agent 编排       |
| ORM             | **SQLAlchemy 2.x**    | 数据访问                 |
| Migration       | **Alembic**           | DB Migration         |
| Database        | **PostgreSQL 16+**    | 核心业务数据               |
| DB Driver       | **asyncpg / psycopg** | Async PostgreSQL     |
| Cache           | **Redis 7+**          | Memory / Cache       |
| Vector DB       | **Milvus**            | RAG                  |
| Background Job  | **Celery 5.x**        | 后台任务                 |
| Tracing         | **OpenTelemetry**     | Trace                |
| Test            | **pytest**            | Unit / Integration   |
| Container       | **Docker Compose**    | 本地部署                 |

FastAPI 基于 Python type hints 与 Pydantic 完成数据校验和 OpenAPI 文档生成，非常适合这种 Schema 很多的 Agent API。

FastAPI 同时天然适合数据库、LLM API 等大量 I/O 场景使用 `async/await`。

SQLAlchemy 采用当前的 **2.x API**，官方当前 2.0 系列同时提供 ORM、事务、连接池和 asyncio 支持。

## 24. 项目最重要的六个技术亮点

最终简历重点只围绕六件事情展开：

1. **LangGraph Multi-Agent Workflow**
2. **Router + Supervisor 动态编排**
3. **Tool Calling 与真实业务系统集成**
4. **RAG + Hybrid Search + Reranker**
5. **Human-in-the-loop 风险操作审批**
6. **Agent Evaluation + Observability**

Redis、PostgreSQL、Celery、Docker 等属于支撑这些能力的工程技术，而不是项目本身的主角。

---

## 25. 最终项目定位

我们最终不是做：

```text
AI 电商聊天机器人
```

而是：

> **基于 LangGraph 构建的有状态 Multi-Agent 电商业务执行系统，通过 Router/Supervisor 进行任务编排，结合 Tool Calling、RAG、Memory 和 Human-in-the-loop 完成订单查询、知识检索及退款业务，并通过 Evaluation 与 Observability 建立 Agent 质量评估体系。**

这将作为整个项目后续设计、Codex Prompt、开发和简历包装的统一技术基线。

### 26.3 Embedding 方案


### 26.4 Sparse Retrieval 不使用百炼 Sparse Embedding

这里做一个重要决定。

虽然百炼的新 Embedding 模型本身已经支持输出 Dense + Sparse，但我们的基础版本**不采用这条路线**。

我们采用：

```text
Dense
→ qwen3.7-text-embedding

Sparse
→ Milvus BM25
```

也就是：

```text
                    Query
                      │
             ┌────────┴────────┐
             │                 │
             ▼                 ▼
     qwen3.7-text-embedding      Milvus BM25
             │                 │
          Dense              Sparse
             │                 │
             └────────┬────────┘
                      ▼
                Hybrid Search
                      ↓
                     RRF
                      ↓
                  Reranker
```

这样有三个好处：

1. Dense 与 Sparse 的职责非常清楚；
2. 可以真正学习 BM25；
3. 不需要再部署 Elasticsearch。

以后可以做实验：

```text
方案 A
Dense + BM25

VS

方案 B
Dense + Learned Sparse
```

这可以成为额外的 RAG 实验，但不是 V1 范围。

### 26.8 LangGraph State 持久化

这项直接确定：

> **使用 PostgreSQL 持久化 LangGraph Graph State。**

具体使用：

```text
AsyncPostgresSaver
```

LangGraph Checkpointer 会在 Graph 执行过程中保存 State checkpoint，从而支持：

```text

Human-in-the-loop

Interrupt / Resume

Fault Recovery
```

LangGraph 官方也明确建议生产型 HITL 使用持久化 Checkpointer，例如 `AsyncPostgresSaver`。

### 26.9 为什么不用 Redis 存 Graph State

因为我们已经有 PostgreSQL。

如果再变成：

```text
Redis
→ Conversation

PostgreSQL
→ Business

Redis
→ LangGraph State

PostgreSQL
→ HumanReview
```

整个状态体系会变得非常混乱。

我们重新划分职责：

#### PostgreSQL

负责：

```text
业务事实

+

LangGraph Checkpoint
```

但两者逻辑隔离。

例如：

```text
PostgreSQL

├── public
│
│   ├── users
│   ├── orders
│   ├── refunds
│   └── human_reviews
│
└── langgraph
    │
    └── checkpoint tables
```

---

#### Redis

只负责：

```text
Cache

Session Metadata

Rate Limit

临时计算结果

热点订单缓存
```

后期需要时还可以：

```text
Redis Pub/Sub
```

用于 Streaming。

但：

> **Redis 不作为 Workflow 的 Source of Truth。**

这样以后：

### 26.12 Human-in-the-loop 持久化

退款 Agent：

```text

     ↓

     ↓
需要人工审批
     ↓

     ↓
LangGraph Checkpoint
```


### 26.16 Agent 权限设计

### 26.20 第一版退款资格规则

首先进行 **Eligibility Check**。

以下情况直接拒绝：

```text
订单不存在

订单不属于当前用户

订单尚未支付

订单已经全额退款

超过退款期限

退款金额 > 可退款金额
```

注意：

> 这些不是“风险”。

这是：

```text
业务规则
```

---

### 26.21 第一版退款风险等级

资格检查通过以后才进入 Risk Check。

#### LOW

满足全部：

```text
退款金额 <= ¥200

近30天退款次数 < 2

订单不存在异常标记
```

结果：

```text
AUTO_APPROVE
```

---

#### MEDIUM

任意一个满足：

```text
退款金额 > ¥200

近30天退款次数 >= 2

退款比例异常
```

结果：

```text
MANUAL_REVIEW
```

---

#### HIGH

例如：

```text
退款金额 > ¥1000

或

近30天退款次数 >= 3

或

90天退款率 >= 50%

或

订单存在异常风险标记
```

结果：

```text
MANUAL_REVIEW_HIGH_PRIORITY
```

注意：

**HIGH 并不直接拒绝。**

风险高：

```text
→ 人工判断
```

而不是：

```text
→ AI 自动拒绝
```

这是更加合理的设计。

### 26.22 风控阈值不能写死

后面我们做：

```text

```

甚至可以调整阈值做实验。
